# ParkingUSA — Отчет о предварительной реализации

Дата: июнь 2026

Этот документ описывает текущее состояние проекта понятным языком: как искать источники, какие данные уже есть, какие проблемы обнаружены, как их решать и сколько это стоит технически.

## 0. Короткий вывод

ParkingUSA уже не просто идея "показать парковки на карте". В проекте есть рабочий MapLibre frontend, API, GeoJSON fallback, PostGIS/Prisma направление, Miami/Miami-Dade OSM baseline, Miami Beach official GIS данные, San Francisco benchmark и research-система для поиска источников.

Главный продуктовый пробел теперь не в карте и не в схеме данных. Главный пробел — для большинства парковок нужно добыть актуальные цены, правила, operator name и нормальные `payment_url` / `booking_url`, чтобы пользователь мог не просто увидеть парковку, а сразу понять: сколько стоит, кто оператор, насколько свежие данные и куда нажать для оплаты.

Практически проект делится на две части:

1. **Слой существования парковок** — OSM/Geofabrik, Overture, городские datasets, official GIS. Это можно закрывать относительно дешево и масштабно.
2. **Слой правды о цене и оплате** — operator pages, payment providers, browser agents, партнерские feeds, AI-звонки, user reports. Вот тут начинается настоящая мясорубка: сайты меняются, цены динамические, ссылки на оплату не всегда прямые, а один гараж может жить сразу в трех источниках.

Вывод по бюджету: логичнее считать не игрушечный MVP, а готовый технический контур на своем железе. Дорогим становится обещание "все парковки США со всеми актуальными ценами и ссылками на оплату", потому что это не разовая выгрузка, а постоянная система добычи и проверки фактов.

## 1. Как искать источники данных о парковках

В США нет единого государственного API с парковками. Данные разбросаны по разным системам. Вот как мы их ищем — с конкретными примерами.

### 1.1 Городские открытые данные (City Open Data)

Это лучший источник. Многие города США публикуют данные о парковочных счетчиках, тарифах и правилах на открытых порталах. Они бывают трех технических типов.

Разберем подробно на примере Майами. Основной источник парковочных данных здесь — **ArcGIS REST**. Это формат, который используют городские GIS-департаменты. Адрес выглядит как `gis.название-города.gov/.../FeatureServer`.

#### Пример из Майами-Бич: официальные уличные парковочные счетчики

Поиск источника начинается с поискового запроса:
```
"parking meter" "FeatureServer" "Miami Beach"
```

Так мы находим публичный GIS-портал Майами-Бич. Это ArcGIS FeatureServer — специальный сервер, который отдает географические данные. У него есть несколько слоев (layers):
- Layer 1 — уличные счетчики (метры);
- Layer 3 — парковочные места;
- Layer 5 — парковочные лоты (площадки);
- Layer 7 — парковочные зоны (полигоны).

Запрашиваем слой счетчиков через обычный URL:
```
https://gis.miamibeachfl.gov/public/rest/services/mb/Parking/FeatureServer/1/query?where=1%3D1&outFields=*&f=json
```

Разберем этот URL по частям:
- `gis.miamibeachfl.gov` — адрес GIS-портала города;
- `/public/rest/services/mb/Parking/FeatureServer` — путь к сервису "Парковки";
- `/1/query` — запрашиваем слой номер 1 (уличные счетчики);
- `where=1%3D1` — условие "все записи" (1=1 — всегда истина);
- `outFields=*` — вернуть все поля;
- `f=json` — ответ в формате JSON.

Сервер возвращает данные в формате Esri JSON (похож на GeoJSON, но со своей структурой). Вот одна реальная запись из ответа:

```json
{
  "attributes": {
    "METER_ID": "2517",
    "STREET": "Ocean Dr",
    "SIDE_OF_STREET": "E",
    "RATE": "4.00",
    "MAX_HOURS": 3,
    "ACTIVE": "Y",
    "LATITUDE": 25.7812,
    "LONGITUDE": -80.1324,
    "PARKING_TYPE": "METERED",
    "PAYMENT_ZONE": "5610",
    "PAYMENT_PROVIDER": "ParkMobile"
  },
  "geometry": {
    "x": -80.1324,
    "y": 25.7812
  }
}
```

Теперь разберем каждое поле — что оно значит и зачем нужно:

- `"METER_ID": "2517"` — уникальный номер парковочного счетчика в системе города. Нужен для: связывания с другими таблицами (тарифами, историей), обнаружения дубликатов при повторном импорте, ссылки на оригинал при жалобах или проверках.
- `"STREET": "Ocean Dr"` — улица, на которой стоит счетчик. Нужно для: отображения адреса в карточке парковки, поиска ("где припарковаться на Ocean Drive"), группировки счетчиков вдоль одной улицы.
- `"SIDE_OF_STREET": "E"` — сторона улицы. Буква означает направление: `E` = восточная сторона (east), бывает `N`, `S`, `W`. Нужно для: точного размещения на карте (слева или справа от дороги), навигации ("ваша парковка на восточной стороне улицы").
- `"RATE": "4.00"` — стоимость парковки: 4 доллара в час. Нужно для: отображения цены пользователю, сравнения парковок по стоимости, фильтра "дешевые/дорогие".
- `"MAX_HOURS": 3` — максимальное время парковки: нельзя стоять дольше 3 часов. Нужно для: предупреждения пользователя ("максимум 3 часа"), фильтра "долгосрочная/краткосрочная", планирования маршрута (если нужно на 4 часа — эта не подходит).
- `"ACTIVE": "Y"` — активен ли счетчик. `Y` = да, работает. Бывает `N` = временно отключен. Нужно для: скрытия неработающих счетчиков с карты, учета сезонных или ремонтных отключений.
- `"LATITUDE": 25.7812` — географическая широта (координата Y на карте). Нужно для: размещения точки на карте.
- `"LONGITUDE": -80.1324` — географическая долгота (координата X на карте). Нужно для: размещения точки на карте.
- `"PARKING_TYPE": "METERED"` — тип парковки: платная по счетчику. Бывают варианты: `FREE` (бесплатная), `PERMIT` (по разрешению), `LOADING` (погрузочная зона). Нужно для: фильтрации по типу, правильной иконки на карте.
- `"PAYMENT_ZONE": "5610"` — номер платежной зоны например в системе ParkMobile. Нужно для: формирования ссылки на оплату через приложение ParkMobile (пользователь вводит этот номер в приложении и платит).
- `"PAYMENT_PROVIDER": "ParkMobile"` — кто принимает оплату. В данном случае — приложение ParkMobile. Бывает также `PayByPhone`. Нужно для: показа пользователю, через какое приложение платить, и формирования правильной платежной ссылки.
- `"geometry": { "x": -80.1324, "y": 25.7812 }` — координаты точки на карте в формате Esri (долгота = x, широта = y). Нужно для: отрисовки маркера на карте.

**Что важно заметить:** в этих данных уже есть всё для продукта: цена (`RATE`), максимальное время (`MAX_HOURS`), платежная зона (`PAYMENT_ZONE`) и провайдер оплаты (`PAYMENT_PROVIDER`). Не хватает только прямой ссылки "нажми и оплати" (`payment_url`) — её можно собрать автоматически, зная зону ParkMobile или спарсить.

#### Другие форматы городских данных

**Socrata** — еще один распространенный формат. Используется в Сан-Франциско, Нью-Йорке, Лос-Анджелесе. Адрес: `data.название-города.gov`. Данные отдаются в чистом JSON. У Майами нет Socrata-источников, поэтому основной путь здесь — ArcGIS (Майами-Бич) и прямые городские страницы (Miami Parking Authority).

**CKAN / Data.gov** — федеральный каталог. Меньше городов, но иногда там лежат уникальные датасеты.

Из-за этого у нас в коде реализованы разные приемники данных.

### 1.2 OpenStreetMap (OSM) — национальный базовый слой

OSM — это открытая карта мира, которую редактируют волонтеры. Парковки там отмечены тегами:
- `amenity=parking` — это парковка;
- `parking=surface` — наземная;
- `parking=multi-storey` — многоуровневый гараж;
- `parking=underground` — подземная;
- `fee=yes/no` — платная или бесплатная;
- `capacity=200` — количество мест.

Как получать:

1. **Маленький запрос (один город)** — через Overpass API. Пример запроса для центра Майами:
```
https://overpass-api.de/api/interpreter?data=[out:json];(node["amenity"="parking"](25.76,-80.20,25.78,-80.18);way["amenity"="parking"](25.76,-80.20,25.78,-80.18);relation["amenity"="parking"](25.76,-80.20,25.78,-80.18););out;>;out skel qt;
```

Разберем: `25.76,-80.20,25.78,-80.18` — это прямоугольник (bbox) вокруг центра Майами (южная широта, западная долгота, северная широта, восточная долгота). Overpass вернет все парковки внутри этого прямоугольника — точки, линии и полигоны.

Ответ приходит в формате OSM JSON — точки, линии, полигоны. Для конвертации в GeoJSON используем готовую библиотеку `osmtogeojson` (уже подключена в проекте).

2. **Большой запрос (штат, страна)** — через Geofabrik PBF-файлы и osm2pgsql. Флорида целиком весит около 400 МБ в сжатом виде. Импортируется в PostGIS через Docker-команду, занимает 15-40 минут. После импорта обычный SQL-запрос достает все парковки:
```sql
SELECT osm_id, name, amenity, parking, ST_AsGeoJSON(way) 
FROM planet_osm_polygon 
WHERE amenity = 'parking';
```

| [LAZ Parking](https://www.lazparking.com/our-company/about/history) | 1.2M+ spaces, 3,000+ locations, 400+ cities | Гаражи, лоты, valet, municipal, airport, healthcare, events, monthly | Browser parser по city/facility pages + партнерство |

| [REEF Parking / Republic](https://pay.reefparking.com/) | Много lot/payment pages, часто через lot number | Lot number, app payment flow, public/private lot facts | Provider-zone parser + app/payment evidence |
| [Towne](https://towne.com/) | 800+ properties по данным инвестора TA Associates | Hotel/healthcare valet, self-parking management, hospitality parking | Valet/venue parser + phone confirmation for gaps |

| [ParkMobile](https://parkmobile.io/about-us/newsroom/articles/parkmobile-hits-new-record-with-50-million-users) | 2M spaces, 600+ cities/municipalities, 140 campuses | Payment zones, app/web payment coverage | Zone/deeplink parser + official city evidence |

Пример — страница поиска парковки на Parking.com. Пользователь вводит город, видит список парковок с ценами:
```
Название: "Garage at 123 Main St"
Цена: $12 / 2 часа, $25 / день
Адрес: 123 Main St, Miami, FL
Бронирование: кнопка "Book Now" → ссылка на checkout
```

Проблема: такие страницы часто используют JavaScript, обычный HTTP-запрос не работает. Нужен браузерный агент (Playwright/Chrome), который открывает страницу как настоящий браузер, ждет загрузки, собирает данные и делает скриншот. То есть да, здесь будет осознанный "велосипед": потому что универсальной кнопки "скачать все парковки с ценами" не существует. Для каждого оператора нужен отдельный parser spec: какие URL обходить, какие поля извлекать, какие screenshots/network payloads сохранять как evidence, какие ссылки можно повышать до `payment_url` или `booking_url`.

### 1.4 Маркетплейсы и платежные системы

SpotHero, ParkWhiz, ParkMobile, PayByPhone — это сервисы, где можно найти и оплатить парковку. Они полезны для:
- получения цен;
- ссылок на бронирование или их формирования;
- зон покрытия ParkMobile/PayByPhone.

Но: scraping (парсинг) маркетплейсов нестабилен(из-за сложностей с антибот обходом) и может быть запрещен условиями сервиса. Грубо и по-человечески: если делать это в лоб и массово, за такое могут очень неприятно прижать, поэтому это не должен быть основной путь продукта. Правильный путь — партнерство или affiliate-программа. Браузерный агент можно использовать как исследовательский инструмент: найти структуру страниц, проверить наличие цен и ссылок, сохранить evidence, но не превращать рискованный marketplace в главный источник без отдельного разрешенного канала. Законодательно могут зажать нас.

### 1.5 Valet, аэропорты, мероприятия, отели, больницы

Это отдельная категория. Данные лежат на сайтах конкретных заведений:

- **Аэропорты**: у каждого крупного аэропорта есть страница "Parking" с тарифами. Например: `https://www.miami-airport.com/parking.asp`
- **Отели**: страница "Parking" или "Amenities" — valet parking, self-parking, цена.
- **Рестораны**: valet parking упоминается на странице или в Google-профиле.
- **Больницы**: visitor parking, гаражи, цены.
- **Стадионы**: event parking, часто с динамическими ценами.

Как получать: поисковый робот находит страницу, далее — ручной осмотр или браузерный агент.

### 1.6 Конкуренты и что у них брать как идею

Черновая таблица отдельно выделяла конкурентов: Parkopedia, SpotHero, ParkWhiz, Google Maps, Waze. Это важный блок, потому что ParkingUSA должен быть не просто "еще одна карта", а карта с более честной структурой данных: источник, цена, свежесть, confidence и ссылка на оплату.

| Конкурент / аналог | Что у него сильное | Что у него слабое для нашей цели | Что берем как идею |
|---|---|---|---|
| Google Maps | Люди уже ищут "parking" там; хорошее покрытие POI; привычный UX(визуальный дизайн) | Нельзя использовать как master database; цены/оплата неполные; данные нельзя свободно хранить как независимый слой(много чего нету) | UX поиска, привычность карты, discovery/matching |
| Waze | Сильная навигационная привычка; интеграции с parking networks | Не является полноценной parking database; нет глубоких правил/цен по всем типам парковок | Идея "парковка рядом с маршрутом" и быстрый переход из навигации |
| Parkopedia | Хорошая концепция parking directory; много типов парковок | Не всегда дает прямую оплату; качество и свежесть зависят от города | Структура справочника, фильтры, карточки объектов |
| SpotHero | Сильное бронирование и понятные цены там, где есть партнерские парковки | Покрывает не все парковки; это marketplace, а не нейтральный слой всех мест | Booking UX, сценарии "на 2 часа / на день / на событие" |
| ParkWhiz | Похож на SpotHero: бронирование гаражей и лотов, особенно рядом с мероприятиями, стадионами, концертами и downtown-зонами | Тоже не все парковки; сильнее в партнерском inventory, то есть показывает в первую очередь те объекты, с которыми есть договоренность | Идея сценария "мне нужна парковка на конкретное событие/дату/время": пользователь выбирает дату, видит цену, резервирует место и проходит checkout до оплаты |
| ParkMobile / PayByPhone | Сильны в оплате уличных зон и meter parking: пользователь вводит номер зоны или выбирает ее в приложении и оплачивает стоянку | Зона оплаты не всегда равна прямой checkout-ссылке; покрытие зависит от городских контрактов; одна и та же улица может быть в приложении, но без стабильной публичной ссылки на конкретное место | Нужно хранить `payment_provider`, `payment_zone`, app/web link и deep link отдельно. То есть не выдумывать `payment_url`, а честно показывать: "оплата через ParkMobile, зона 5610" и открывать приложение/страницу, если ссылка доказана |
| Parking.com / SP+ | Крупный operator/marketplace inventory: garages/lots, daily parking, monthly parking, event parking, airport/hospital/university объекты | JS/browser flows, динамические цены, не все ссылки можно безопасно забирать; страница объекта может быть просто карточкой, а не прямой оплатой | Нужен operator parser: браузер открывает city/facility pages, сохраняет цену/адрес/operator/evidence, классифицирует ссылку как `facility_page`, `operator_search` или `direct_checkout`. Долгосрочно лучше partner/API feed |

Вывод по конкурентам: ни один конкурент не закрывает нашу цель целиком. Одни сильны в поиске, другие в оплате, третьи в бронировании. ParkingUSA должен собрать это в один слой: все известные парковки на карте, отдельно отмечая, какие факты подтверждены, а какие еще требуют проверки.

### 1.7 Какой функционал должен выйти из черновика

Из заметки в ячейке черновика видно главное требование: "пощупать как собирать данные с сотни тысяч парковок как зоны, смотреть, оценивать, привязка к карте, красивый лаконичный дизайн, фильтрация и сортировка по времени/стоимости".

В продукте это превращается в такой функционал:

| Функция | Зачем пользователю | Что нужно в данных |
|---|---|---|
| Визуализация всех видов парковок | Понять, где вообще можно встать | geometry, facility_type, source, confidence |
| Зоны на карте | Видеть районы тарифов, permit/event zones, lots | polygons/lines, zone_type, rules |
| Фильтр по цене | Найти дешевле | hourly/daily/monthly rates, price_status |
| Фильтр по времени | Понять, можно ли стоять сейчас или на 2-4 часа | hours, max_hours, rules, schedule |
| Сортировка по цене/дистанции/уверенности | Быстро выбрать лучший вариант | normalized rates, distance, freshness, confidence |
| Суточная/почасовая/долгосрочная парковка | Разные сценарии: встреча, рабочий день, месяц | rate_type: hourly/daily/monthly/event |
| Кнопка оплаты/брони | Перейти к оператору без ручного поиска | payment_url, booking_url, payment_provider |
| Оператор парковки | Понять, кто отвечает за объект | operator, source_name, source_url |
| Предложить данные | Закрывать дыры, когда цена неизвестна | user_report observations, moderation/review |

Боты/мессенджеры из черновика лучше рассматривать как второй канал, а не как основной продукт. Главный интерфейс — карта. Бот может позже отвечать на вопросы вроде "где рядом парковка дешевле $10 на 2 часа", но без качественной базы и карты он будет просто красивой оболочкой над дырявыми данными.

## 3. Проблемы и как их решать

### 3.1 "Нет ссылок на оплату"

**В чем проблема:** Почти ни у одной парковки в системе сейчас нет работающей ссылки "Оплатить" (`payment_url`) или "Забронировать" (`booking_url`).

**Почему так:** Городские open data (Socrata, ArcGIS) редко содержат платежные ссылки. Они дают координаты и тарифы, но не ссылку на оплату конкретного места. OSM тоже не содержит платежных ссылок.

**Как решать:**

| Шаг | Что делаем | Ресурсы |
|---|---|---|
| 1. Платежные провайдеры | Для ParkMobile/PayByPhone зон собираем deeplink-схемы. Например, у Miami Beach уже определены ParkMobile zone ID — можно сформировать ссылку на оплату через приложение. | Playwright-парсер зон |
| 2. Операторские страницы | Для ABM, SP+, Premium — на странице каждого объекта есть кнопка "Reserve"/"Book Now". Нужен браузерный агент, который ее находит и сохраняет URL. | Playwright-агент |
| 3. Партнерства | SpotHero, ParkWhiz — affiliate-ссылки. Самый чистый путь, но требует переговоров. | Бизнес-ресурс |
| 4. Пользовательские предложения | Форма "Предложить данные" уже работает. Пользователь может прислать ссылку на оплату. | Уже сделано |

**Примерное время на один город (технически):**
- Сбор ParkMobile/PayByPhone зон: 2-4 часа автоматизированного сбора
- Операторские парсеры: 4-8 часов на оператора
- Проверка качества: 2-4 часа ручной верификации
Может больше

**Также ссылки на оплату можно будет парсить и проверять цены**

### 3.2 "Многие парковки без цен"

**В чем проблема:** OSM baseline (6,821 полигона в Miami-Dade) показывает, ЧТО парковка существует, но не дает цену. Даже в Сан-Франциско с большим объемом данных только у 33,511 счетчиков есть тарифы — а OSM-зоны остаются без цен.

**Как решать:**

| Метод | Для каких парковок | Точность |
|---|---|---|
| City open data (Socrata/ArcGIS) | Уличные счетчики | 95% |
| Сайты операторов | Гаражи, лоты | 70-85% |
| Партнерские фиды | Коммерческие парковки | 90% |
| AI-звонки | Самые важные пробелы | 60-80% |
| Пользовательские отчеты | Точечные дополнения | 35-75% |

### 3.3 "Valet-парковки почти не охвачены"

**В чем проблема:** Valet — это когда ключи отдаешь сотруднику. Эти парковки не попадают в городские open data. Они есть у ресторанов, отелей, больниц.

**Как решать:**

1. Сбор из OSM: тег `parking=valet` существует, но редко заполняется.
2. Поиск по сайтам отелей/ресторанов: парсер ищет ключевые слова "valet parking" на страницах.
3. Google-подсказки: поисковые запросы "valet parking near [address]" дают список кандидатов.
4. AI-звонки: обзвон 50-100 важных объектов в городе для подтверждения.
5. Пользовательские отчеты: форма уже готова.

**Примерная оценка:** В Майами может быть 500-1,500 valet-точек. Автоматически найти можно ~40% через сайты. Остальное — ручная работа или звонки.

### 3.4 "Данные устаревают"

**В чем проблема:** Тарифы меняются. Города обновляют ставки. Парковки закрываются и открываются.

**Текущее состояние:** Система хранит `last_verified_at` и `data_as_of` для каждой записи. Но автоматического мониторинга свежести еще нет.

**Как решать:**

1. **Автоматическая проверка API-источников** — для Socrata/ArcGIS 2 раза в день. Если данные изменились — обновить.
2. **Браузерная перепроверка операторов** — раз в неделю.
3. **Пользовательские репорты о неверных ценах** — механизм уже есть.
4. **Приоритизация по трафику** — чаще проверять популярные парковки.

### 3.5 "Правовые риски парсинга"

**В чем проблема:** Не все сайты можно законно парсить.

**Как решается в проекте технически:** Каждый источник имеет оценку `legal_risk` (от low до high) в research manifests. Технически для рискованных/нестабильных источников делаем так:
- Сначала партнерство / outreach.
- Если невозможно — только публичные страницы с сохранением evidence и ToS review и ссылками откуда данные.
- Никакого scraping закрытых API или checkout-страниц без разрешения.

Главная практическая мысль: если источник нельзя безопасно использовать как постоянный feed, он остается research/evidence source, а не master database. Иначе это будет не продуктовая база данных, а минное поле, которое однажды очень неприятно взорвется.

Так дешевле, если парсеры, локальные LLM, STT и browser agents будут работать постоянно. Но нужен дисциплинированный backup: без него свой сервер превращается в одну точку отказа.

| TTS / voice agent / LLM during call | речь агента и извлечение фактов | зависит от провайдера и модели | закладывать еще ~$0.05-0.20 на звонок |
| Мощный Mac Studio или самосборный GPU-сервер | тяжелые локальные/экспериментальные inference jobs: LLM extraction, embeddings, локальный STT, дедупликация, batch enrichment | Mac Studio проще и тише; самосборный GPU-сервер мощнее и гибче; cloud GPU оставляем только как запасной вариант, если локальной мощности не хватает | one-time железо вместо постоянной аренды GPU |

**AI-звонки, пересчитано:**

Реалистичная техническая цена одного короткого звонка на 2-3 минуты при локальном STT: **$0.07-0.25 / 5-18 ₽**. В эту сумму входит телефония, TTS/voice, LLM-извлечение фактов через дешевую API-модель или локальную LLM и небольшой запас на неудачные звонки. STT отдельно не считаем, потому что расшифровку делаем на своем сервере.

| Объем | Годовая оценка |
|---|---:|
| 1,000 пилотных звонков | **5,000-18,000 ₽ / $70-250** |
| 5,000 звонков | **25,000-91,000 ₽ / $350-1,250** |
| 10,000 звонков | **51,000-182,000 ₽ / $700-2,500** |

Звонки не должны быть первым способом сбора данных. Их лучше использовать для дорогих пробелов: valet, hospital/airport/event parking, конфликтующие цены, устаревшие operator pages.

### 4.4 Mac Studio M4 Max для локальных LLM

**Что изменилось после проверки цен:** идея "Mac Studio M4 Max за 200,000 ₽" реалистична только для базовой или близкой к базовой конфигурации. Для локальных LLM важна не только модель чипа, а **объем unified memory**.

Публичные ориентиры:

- Apple указывает старт Mac Studio от **$1,999** ([Apple Newsroom](https://www.apple.com/newsroom/2025/03/apple-unveils-new-mac-studio-the-most-powerful-mac-ever/)) — это примерно **145,000 ₽**, но это базовая конфигурация.
- Конфигурация M4 Max с **128 GB RAM** у CDW стоит **$3,528.99** ([CDW](https://www.cdw.com/product/apple-mac-studio-m4max-128-gb-ram-512-tb-ssd/8288082)) — примерно **256,700 ₽**

**Что можно запускать локально:**

| Конфигурация | Что реально подходит |
|---|---|
| 36-48 GB unified memory | небольшие 7B-14B модели, embeddings, классификация, простые extractors |
| 64 GB | 30B-ish quantized модели, несколько маленьких агентов, но с ограничениями |
| 96-128 GB | 70B quantized модели, более серьезный extraction/reasoning, локальная дедупликация |
| 128 GB+ | уже похоже на локальную research station, но все равно медленнее облачных API на сложных задачах |

**Для ParkingUSA Mac Studio полезен так:**

| Задача | Нужна LLM? | Mac Studio помогает? |
|---|---|---|
| Socrata/ArcGIS/CKAN импорт | Нет | Нет, это обычный ETL |
| OSM/osm2pgsql импорт | Нет | Нет, важнее диск/CPU/PostGIS |
| Извлечение структуры с operator pages | Да | Да, но Playwright/browser все равно нужен |
| Дедупликация и проверка конфликтов | Да | Да |
| Обработка пользовательских отчетов | Да | Да |
| Массовые AI-звонки | Да | Частично: можно делать extraction/STT локально, но телефония и voice stack остаются отдельными |
| 24/7 production agents | Да | Можно, но нужен мониторинг, очередь задач и fallback на API |

**Вывод по покупке:** если выбираем стратегию "свой сервер + локальные агенты", Mac Studio уже не выглядит игрушкой на потом, а становится рабочим центром проекта. Он особенно полезен, если LLM/STT/browser enrichment будут крутиться постоянно, а не раз в неделю. При цене 250 000 ₽ break-even против $300/мес — около **11-12 месяцев**, против $700/мес — около **5 месяцев**. При цене 200,000 ₽ окупаемость быстрее.

Практическая рекомендация: если бюджет позволяет, можно сразу делать готовый контур на своем железе: PostGIS, OSM baseline, browser runner, локальный STT, локальные LLM для простых задач и дешевый OpenRouter fallback для сложных. Это лучше совпадает с идеей "агентской организации", где одни агенты ищут источники, другие парсят, третьи проверяют цены и stale records.

### 4.5 Сводка расходов: готовый серверный вариант

Здесь не считаем отдельный маленький MVP. Считаем вариант, где сразу покупаем свои мощности и делаем нормальный технический контур: карта, PostGIS, OSM/Geofabrik, parser runner, browser agents, локальный STT, локальные LLM для простого извлечения, дешевый OpenRouter fallback для сложных задач и маленькая облачная обвязка для публичного доступа.

**Первый год: покупка железа + запуск**

| Статья | Годовая стоимость |
|---|---:|

| Публичный VPS-шлюз, VPN/proxy/US egress, домены | **34,000-168,000 ₽ / ~$467-2,309 в год** |
| Backups / snapshots / object storage | **13,000-72,000 ₽ / ~$179-990 в год** |
| Tavily / web research | **0-35,000 ₽ / $0-480** |
| OpenRouter cheap models | **9,000-175,000 ₽ / ~$120-2,400** |
| AI-звонки, 5,000-10,000 проверочных звонков | **25,000-182,000 ₽ / ~$350-2,500** |
| **Итого первый год** | **~366,000-1,182,000 ₽ / ~$5,030-16,245** |

**После покупки железа: годовая эксплуатация**

| Статья | Годовая стоимость |
|---|---:|
| Электричество, VPN/proxy, VPS-шлюз, домены | **46,000-204,000 ₽ / ~$632-2,804** |
| Backups / R2 / evidence storage | **13,000-72,000 ₽ / ~$179-990** |
| OpenRouter fallback | **9,000-175,000 ₽ / ~$120-2,400** |
| AI-звонки | **25,000-182,000 ₽ / ~$350-2,500** |
| **Итого после покупки железа** | **~93,000-633,000 ₽ / ~$1,280-8,694 в год** |

**Что это значит по сути:**

- Дорогая часть первого года — железо.
- После покупки железа расходы резко падают.
- Локальный STT почти убирает цену расшифровки звонков.
- Дешевые модели через OpenRouter закрывают сложные случаи, где локальная модель тупит или работает слишком медленно.
- VPN/proxy/US egress нужен не для красоты: часть американских city/operator/payment источников может плохо открываться из России или давать другой HTML.

Самый честный бюджетный вывод: "все парковки со всеми ценами и оплатой" становится дорогим не из-за карты, а из-за постоянного обновления частных источников, browser-проверок, AI-звонков и качества данных. Тут деньги сгорают не на кнопках интерфейса, а на том, чтобы каждый день заново понимать, где правда, где старая цена, а где оператор опять поменял сайт. Для этого дешевле купить собственные мощности.

## 5. Оценка сложностей

### 5.1 Технические сложности

| Сложность | Уровень | Почему | Как исправить |
|---|---|---|---|
| Сбор цен с операторских сайтов | **Высокая** | У каждого оператора своя структура сайта, часто JavaScript, иногда client-only GraphQL или booking flow | Браузерные агенты (Playwright), отдельный parser spec на каждого оператора, dry-run evidence перед записью в canonical data. Первый безопасный slice уже есть для Premium Parking |
| Ссылки на оплату/бронирование | **Высокая** | Facility page не равен checkout link; app zone не равен payment URL; нельзя подставлять ссылки наугад | Классифицировать ссылки как `direct_checkout`, `facility_page`, `app_zone`, `operator_search`; повышать в `payment_url` / `booking_url` только direct/proven links |
| Valet-парковки — обнаружение | **Высокая** | Нет единого источника, разбросаны по сайтам отелей, ресторанов, больниц и мероприятий | Комбинация OSM + venue/hotel parsers + Google только для discovery/matching + AI-звонки для важных пробелов |
| Дедупликация (один гараж в 3 источниках) | **Средняя/высокая** | Один и тот же гараж может быть в OSM, у оператора, на city page и в marketplace | Гео-сравнение (30-80м) + fuzzy name + normalized address + phone/website/operator + source priority. Это надо делать до массового operator import |
| Масштабирование на всю страну | **Средняя** | Объем данных растет в 100 раз, GeoJSON в браузере перестанет быть нормальным путем | OSM/Geofabrik как baseline + PostGIS + vector tiles через Martin/Tippecanoe. Путь уже выбран и частично проверен на Флориде |
| Поддержание актуальности | **Средняя/высокая** | Тарифы меняются, парковки закрываются, сайты операторов ломают selectors | Scheduled ingestion + freshness scoring + source health checks + user reports + review backlog |
| Разные форматы данных в разных городах | **Низкая/средняя** | Socrata, ArcGIS, CKAN, CSV, HTML, PDF — разные входы | Универсальные коннекторы уже есть как foundation, но часть еще надо довести до canonical upsert |

### 5.2 Организационные сложности

| Сложность | Уровень | Как решать |
|---|---|---|
| Партнерства с операторами | **Высокая** | Холодные письма, демонстрация продукта. Без них часть данных останется неподтвержденной либо незаконной |
| Легальность AI-звонков | **Высокая** | TCPA, robocall законы, one-party/two-party consent по штатам. Грубая версия: технически можно быстро накрутить звонящего агента, но если забить на правила, это будет не "хак", а потенциальная проблема для всего проекта. В этой смете юридические расходы не считаем, но как риск это нельзя прятать под ковер |

### 5.3 Приоритетная дорожная карта исправления сложностей

1. **Месяц 1-2:** Довести Socrata/ArcGIS коннекторы до canonical import для 5 benchmark cities. Это закрывает самый чистый слой: уличные счетчики, тарифы, rules, official provenance.
2. **Месяц 2-3:** Сделать нормальный `payment_url` / `booking_url` pipeline: классификация ссылок, dry-run evidence, запрет на promotion сомнительных facility pages.
3. **Месяц 3-4:** Запустить parser runner для крупных операторов: Metropolis/SP+/Parking.com, LAZ, ABM, Premium, Propark/Ace как следующий слой. Цель — гаражи/лоты с ценами, operator name и ссылками, где они реально доказаны.
4. **Месяц 5-6:** OSM/Geofabrik импорт для 25 metro areas + dedupe engine. Это превращает карту из "несколько городов" в нормальный coverage baseline.
5. **Месяц 7-12:** Valet, аэропорты, отели, больницы, мероприятия: browser parsers + точечные AI-звонки + user reports. Здесь возможна агентская организация: одни агенты ищут источники, другие парсят, третьи проверяют конфликтующие цены и stale records.
6. **Параллельно:** Перейти на vector tiles (Martin/Tippecanoe), чтобы не возить огромные GeoJSON в браузер.

## 6. Главная цель — что должно получиться

Пользователь открывает карту и видит:

- **Все известные парковки** — и с ценами, и без цен (серым цветом).
- **Для парковок с ценами** — карточка показывает: название, адрес, оператора, цену за час/день/месяц, часы работы, свежесть данных, источник.
- **Кнопка "Оплатить"** — если есть ссылка на оплату, ведет на страницу оператора или платежную систему.
- **Кнопка "Маршрут"** — строит путь от текущей точки.
- **Кнопка "Предложить данные"** — если цена неизвестна, пользователь может отправить информацию.
- **Фильтры** — по цене, типу, доступности, оператору.
- **Парковочные зоны** — полигонами разного цвета (красный = гараж/lot, синий = уличная зона, зеленый = бесплатно).
- **Valet-точки** — отдельным слоем.

Все это обновляется автоматически, источники проверяются, данные не устаревают.
